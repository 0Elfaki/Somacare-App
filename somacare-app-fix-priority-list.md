## Tier 0 — Access control (fix first, this is the permission boundary for the whole app)

- [x] **New, found while investigating "doctor credentials log into student side":** confirmed real, and root-caused via your live Supabase project's data and RLS policies (not just the local code) — this had nothing to do with the credentials themselves. `app_router.dart`'s redirect guard bounces any already-logged-in visit to `/onboarding` or `/role-selection` back to that session's dashboard; `/student-login` and `/doctor-login` were *also* in that bounce set. Since `supabase_flutter` persists sessions on-device, a lingering student session meant opening `/doctor-login` redirected straight to `/student-dashboard` before the doctor credentials were ever checked — the login form never got a chance to run. A second, narrower race existed even after signing out properly: the redirect guard reads a *cached* role that's normally refreshed asynchronously off `onAuthStateChange`, so a fresh login's own `context.go('/doctor-dashboard')` could still be evaluated against the *previous* session's stale cached role for one frame. Fixed both: `/student-login` and `/doctor-login` no longer bounce logged-in visitors (they instead sign out any existing session the moment the screen opens — reaching a login screen means you want to authenticate, possibly as someone else), and `_login()` now sets the cached role synchronously right before navigating instead of waiting on the async refresh. Checked your actual `profiles` RLS policies and seed data as part of ruling this out as a data problem: the seeded doctor/student rows all have the correct `role` values, so this was purely a client-side routing bug, not corrupted data.
- [x] ~~`student_login_screen.dart` — unconditional role upsert self-assigns doctor access~~ — **correction:** traced the actual logic and it doesn't hold up. `dbRole` is read fresh from the DB every login; when no profile row exists yet it defaults to `'student'`, and the code hard-blocks (signs the user back out) whenever `dbRole != _role` — so a brand-new account can never log in as Doctor, only Student. There's no path to self-assigned doctor access here. Hardened anyway: the role `upsert` now only fires when `profile == null` (first-ever login), so an existing role can never be rewritten by the client even in principle, and the role tab / school selector are now disabled while `_isLoading` so the selection can't change mid-request.
- [x] `doctor_appointments_screen.dart` — confirmed real: when the doctor-scoped query came back empty it fell through to an unfiltered `.limit(20)` query and displayed every patient's appointments. Removed that fallback entirely (kept the legacy doctor-name lookup, since that's still scoped to the one doctor); also stripped the `debugPrint` trail left in `initState`/`build`/`_buildSimpleList`.
- [x] `doctor_medical_history_management_screen.dart` — confirmed real: `_loadPatients()` correctly computed `studentIds` from the doctor's own appointments but then discarded it and populated the dropdown from every `role == 'student'` profile in the database. Now fetches only the profiles in `studentIds` (`.inFilter('id', studentIds)`).
