# SomaCare App - UI/UX Tester Pass

Scope: `Somacare-App` (the Flutter mobile app, doctor + student sides). This is the product your saved Telemedicine Design System / UI-UX Behavior rules were checked against - note up front that those rules describe a web admin dashboard (sidebar nav, breadcrumbs, Cmd+K search, data tables, KPI sparklines, role hierarchy with Hospital/School Admin, audit logs). None of that exists in this codebase, because this app is a two-role (student/doctor) mobile consultation app with bottom-tab navigation. If you want those rules checked against the actual dashboards, that's `Somacare-Hospital-Dashboard` / `Somacare-School-Dashboard` / `Somacare-Main-Dashboard` in the same folder - separate pass.

Everything below was found by reading the app's source, not by running it, so treat "confirmed" items as code-certain and anything phrased as "likely/appears" as needing a quick manual check.

---

## Critical - data integrity, safety, security

**1. Fake conversation shown as real chat history.** `messaging_chat_screen.dart`: when opened without a specific `doctorId` - which is exactly what happens when a student taps the dashboard's "Message a doctor" quick action - the screen loads a hardcoded demo thread with a fictional "Dr. Sarah Martinez," including fake prior messages, a fake image attachment, and a fake voice note. There is no "demo" label. A real student tapping the most common entry point to messaging sees fabricated conversation history indistinguishable from a real one.

**2. Fabricated vitals shown to doctors as real patient data.** `student_profile_screen.dart`: when a patient has never recorded height/weight/blood pressure/blood type, the doctor's view silently substitutes defaults (170cm, 70kg, "120/80", "A+") and computes a BMI from them - with no "not recorded" indicator. A doctor could read "BMI 24.2 (Normal)" as a real measurement when it's fabricated. Same file also hardcodes the past-appointment status badge to always render green/"success" styling regardless of the appointment's actual status, so a cancelled visit shows with a success badge.

**3. Reminder "saved" without being saved.** `my_medications_screen.dart`, `_showAddReminderDialog`: the "Save Reminder" button shows a success snackbar ("Reminder set for …") and closes the sheet, but the handler's only code is a comment - `// Add reminder logic here` - nothing is persisted. The user is told it worked; it didn't.

**4. Payment flow never collects payment details.** `payment_screen.dart`: selecting MTN Mobile Money, Airtel Money, or Visa/Mastercard and tapping Pay calls `onConfirm()` directly - no phone number is collected for mobile money, no card fields exist for cards (your own payment rules call for Stripe Elements or equivalent, never custom-built), and "Payment successful" fires immediately with nothing actually charged. There's also no receipt/invoice afterward.

**5. Doctor-scoping gaps let a doctor see data beyond their own patients.**
   - `doctor_appointments_screen.dart` (`_loadAppointments`): if the doctor-scoped query returns empty, it falls back to fetching *all appointments in the database* ("for debugging," per the comment) and displays them.
   - `doctor_medical_history_management_screen.dart`: it computes the doctor's own patient IDs from their appointments, then discards that list and populates the "Select Student" dropdown from every profile with `role == 'student'` in the entire system - any doctor can open and edit any student's medical history, not just their own patients.

**6. Emergency screen is hardcoded to one country with no real location capture.** `emergency_screen.dart` is explicitly "localized for the Uganda health system" - Uganda Police, KCCA Ambulance, Uganda Red Cross, Uganda-specific first-aid content - with no way to configure it per deployment. Your own profile has you registered in Kenya, and the theme file separately defines M-Pesa brand colors (Kenya/Tanzania) that are never used anywhere, while the payment screen only offers Uganda-typical MTN/Airtel/Card and prices everything in UGX - except `doctor_finances_screen.dart`, which shows the same fee figures with a `$` prefix. Three different signals (UGX, USD, unused M-Pesa tokens) for what should be one currency/market. Separately, "Use current location" on the emergency screen only shows a toast ("Using your current location") - it never calls any geolocation API or attaches coordinates to the emergency alert that gets written to the database. For a feature whose entire purpose is fast, accurate emergency response, wrong regional numbers and no real location data are safety-relevant, not cosmetic.

**7. Destructive action with zero confirmation.** `my_appointments_screen.dart` (`_cancelAppointment`): tapping "Cancel" on an appointment cancels it immediately - no confirmation dialog. This is the exact scenario your own product rules name explicitly: "cancel appointment... ALWAYS require a two-step confirmation modal. Never a single click." The doctor side handles a comparable case correctly (deny/approve on medical records) but appointment cancellation on the student side skips it entirely. Status changes on `appointment_detail_screen.dart` (the doctor's dropdown, which includes "Cancelled") have the same gap - selecting Cancelled fires immediately.

**8. AI symptom checker has no persistent disclaimer.** `symptom_check_screen.dart`'s system prompt asks the model to append an AI disclaimer, but that's the *model's* responsibility each turn, not a fixed UI element - nothing in the screen itself permanently states "this is not a diagnosis." Relying on an LLM to remember a disclaimer every reply is not reliable, and for a symptom-triage feature the gap is meaningful.

## High - broken or fake functionality

- **Non-functional Settings toggles.** `doctor_profile_screen.dart`'s settings sheet: the "Notifications" switch is hardcoded `value: true` with `onChanged: (v) {}`, "Dark Mode" is hardcoded `value: false` with the same no-op handler, and "Language"/"Privacy"/"Security" tiles have empty `onTap`. Separately, `main.dart` hardcodes `themeMode: ThemeMode.light` with a single theme - `buildDarkTheme()` is literally an alias for `buildAppTheme()` - so *any* Dark Mode control anywhere in the app (this one, and the `_darkMode` state variable declared in the student `profile_screen.dart`) can never do anything even if wired up correctly.
- **Fake support contact info, and it's inconsistent.** `doctor_profile_screen.dart`'s Help dialog shows a US-format placeholder phone (+1 234 567 890) and "Chat: Available 24/7" with no chat entry point; tapping "Contact Support" just shows a toast. `student_login_screen.dart`'s support dialog lists a *different* email (`support@somacare.app` vs. the profile screen's `support@somacare.com`) - two different "real" support addresses in the same app.
- **Dead tap targets.**
  - `my_appointments_screen.dart`: tapping an appointment card does nothing (`onTap: () { // Could navigate to appointment details }`).
  - `medical_store_screen.dart`: the notification bell shows "Notifications coming soon!" - a second, disconnected, non-functional bell, even though the app already has a working notifications screen reachable elsewhere.
  - `my_medications_screen.dart`: the app-bar "add reminder" icon shows "Add new medication feature coming soon!"
- **Notifications are marked read before the user ever sees which ones were new.** `notifications_screen.dart` calls `markAllAsRead` as part of the same load that fetches the list, so by the time anything renders, `is_read` is already true for every item - the unread-dot UI that's built into `_NotificationCard` can never actually appear. Also, tapping a notification only navigates for `type == 'booking'` or `'emergency'`; your own documented notification types (`prescription_ready`, `lab_result_uploaded`, `payment_due`, `consultation_started`) do nothing when tapped.
- **White text on a white sheet.** `student_profile_screen.dart`, `_addLabResult`: every field in the "Add lab result" bottom sheet (`TextFormField`s for test name, value, unit, ranges, and the status dropdown) sets `style: TextStyle(color: Colors.white)` inside a sheet with `backgroundColor: AppColors.surface` (`#FFFFFF`). Typed text is invisible. Looks like copy-pasted styling from a dark-themed screen that was never adjusted.
- **Two parallel component libraries, by the codebase's own admission.** `bloom_components.dart`'s header comment says it plainly: "the older shared widgets, still used across the student flows... seventeen screens still render from them" versus `app_ui.dart`, "the design system the two dashboards share." In practice this means the doctor dashboard/shell/patients list look and behave one way, while appointment detail, encounter form, prescription writer, payment, and most student screens look and behave another - different card radii, different button shapes, different header styles. On top of that, `doctor_finances_screen.dart`, `doctor_appointments_screen.dart` (list rows), `notifications_screen.dart`, `doctor_profile_screen.dart`, and `student_profile_screen.dart` don't use *either* shared library for large sections - they hand-roll their own `Container`/`Card`/`ListTile` styling with hardcoded pixel sizes, which is a third de facto style per-screen.
- **Two more screens diverge again on header style.** `my_medications_screen.dart` and `medical_store_screen.dart` (the only two screens built on Riverpod instead of local Supabase calls) use a solid-blue Material `SliverAppBar` with white text - a fourth header treatment, distinct from both the `AppPageHeader` used on the dashboards and the `BloomScreenHeader` used on Bloom-flow screens.
- **Every default-height `BloomButton` is below your own minimum touch target.** `bloom_components.dart`: `BloomButton`'s default `height` is `42`. Your own `AppTouch.minTarget = 48.0` and DESIGN_SYSTEM.md rule 3 ("every tappable thing is at least 48×48") apply to the *other* component set but not this one - and BloomButton is the primary CTA on essentially every Bloom-flow screen: "Pay," "Submit prescription," "Save encounter," "Continue to payment," "Request emergency help." This is one button component away from being fixed everywhere at once.
- **Refill stepper is 32×32.** `prescription_writer_screen.dart`, `_StepperButton`: explicitly smaller than the 48×48 floor, on a form used to prescribe medication.

## Medium - consistency, validation, and error handling

- **Raw exceptions leaked to the user.** The app defines `userFriendlyErrorMessage()` specifically to sanitize Supabase/network errors into plain language, and most screens use it - but `appointment_detail_screen.dart`, `encounter_form_screen.dart`, `prescription_writer_screen.dart`, `doctor_profile_screen.dart`, `doctor_finances_screen.dart`, `doctor_medical_history_management_screen.dart`, and `symptom_check_screen.dart` all show `'...: $e'` directly in a SnackBar or chat bubble instead. `symptom_check_screen.dart` also prefixes it with a ⚠️ emoji.
- **Two different validation bars for the same action.** Denying a medical history has two entry points with different rules: `doctor_dashboard_screen.dart`'s inline approval card requires a 5+ character reason with a `Form` validator; `doctor_medical_history_management_screen.dart`'s deny dialog accepts a single character (and silently does nothing if the field is left empty - no error shown).
- **Vitals entry quality differs by role for the same data.** The student's own profile screen (`profile_screen.dart`) uses proper `CupertinoPicker` wheels for height, weight, blood pressure, and blood type. The doctor's encounter form (`encounter_form_screen.dart`) captures the same categories of data - temperature, blood pressure, heart rate - as unvalidated free text with only a hint string ("37.0°C", "110/70") and no numeric keyboard, no units enforced.
- **Currency mismatch, confirmed.** `payment_screen.dart` formats and labels every amount as UGX; `doctor_finances_screen.dart` shows the same category of figures with a literal `$` prefix and no thousands separator. Same app, two currencies.
- **No booking-conflict check.** `book_appointment_screen.dart` offers the same fixed time slots for every day/doctor with no check against existing bookings - nothing stops two students from booking the identical doctor/date/time.
- **Bottom nav highlights the wrong tab.** `DoctorShell`'s `_indexFor` only recognizes `/doctor-dashboard`, `/doctor-appointments`, `/doctor-patients`, `/doctor-profile`. `/doctor-finances` and `/doctor-medical-history` are also inside the same shell (so the bottom nav is still visible there) but aren't in that list, so they default to index 0 - visiting Earnings or Medical Histories shows "Home" as the active tab.
- **Inconsistent back-navigation affordances within the same tab bar.** `doctor_appointments_screen.dart` and `doctor_finances_screen.dart` both add an explicit "back to dashboard" arrow in their `AppBar`, even though both are (or, in Finances' case, render inside) the shell with its own bottom nav; `doctor_patients_screen.dart`, a genuine peer tab, has no such arrow. `appointment_detail_screen.dart` goes further and forces every back-gesture to `/doctor-dashboard` regardless of where the screen was opened from (patients list, appointments list, a push after ending a call) - a doctor who drilled in from Patients gets kicked back to Home instead of Patients.
- **No post-call workflow for the doctor.** The student's `consult_screen.dart` tracks call duration and routes to `/post-consultation-summary` on end. The doctor's near-identical `doctor_consult_screen.dart` has no timer and just pops back - nothing prompts the doctor to open the encounter form or write a prescription right after the call, even though those are the obvious next steps.
- **Shared fallback video channel name.** `consult_screen.dart` defaults to a literal `'consultation'` channel ID when no `channelId` is passed in. Every route that reaches this screen today supplies a per-appointment ID, but the shared static fallback is a landmine if any future entry point (a stale deep link, a missed `extra`) skips that - two strangers could end up in the same open channel.
- **Encounter form has no discard-changes guard.** A doctor who fills out vitals/diagnosis and swipes back loses everything silently - no "discard changes?" prompt, unlike the appointment/emergency screens which intercept the back gesture for other reasons.
- **No review step before prescribing.** `prescription_writer_screen.dart` submits the moment "Submit prescription" is tapped - no summary/confirm screen, despite this being exactly the kind of health-record-affecting submission your own rules call for a review step on.

## Lower severity / polish

- Loading states are inconsistent: `doctor_patients_screen.dart` and `notifications_screen.dart` correctly use `AppSkeletonRow`; `doctor_appointments_screen.dart`, `doctor_finances_screen.dart`, `doctor_medical_history_management_screen.dart`, `appointment_detail_screen.dart`, `student_profile_screen.dart`, `my_appointments_screen.dart`, `book_appointment_screen.dart`, and `my_medications_screen.dart` all fall back to a bare centered spinner, which your own DESIGN_SYSTEM.md explicitly asks screens not to do.
- Hardcoded raw `Color(0x…)` values outside `AppColors` show up in `student_profile_screen.dart` (`Color(0xFFD97706)` for the allergy-warning border, where `AppColors.warningDark` already exists) and `doctor_medical_history_management_screen.dart` (`Colors.black87` for field labels) - both direct violations of DESIGN_SYSTEM.md rule 1.
- Emoji usage is inconsistent with the rest of the app's tone: "✅ Profile updated" (`doctor_profile_screen.dart`), "🚨 Emergency appointment started!" (`book_appointment_screen.dart`), the AI assistant's "👋" greeting and "⚠️ Error" (`symptom_check_screen.dart`).
- Heavy leftover `debugPrint` instrumentation, including full raw row dumps, in `doctor_appointments_screen.dart` and `my_appointments_screen.dart` - looks like debugging that shipped.
- "About" dialog copy reads "Version 2.0.0 2026" (missing punctuation) in `doctor_profile_screen.dart`.
- Radius values drift within single screens that don't use the shared `AppCard` (e.g. `student_profile_screen.dart` mixes 12/14/20px corners across header, vitals cards, and prescription chips in the same view).
- No search on the doctor's patient list, and no doctor bio/photo/ratings shown when booking - not wrong, just a gap worth a product call.

## Suggested triage order

1. Messaging demo-thread fake-history bug, fabricated vitals defaults, unsaved "reminder saved" confirmation, and the two doctor-side data-scoping leaks (appointments-fallback-to-all, medical-history-dropdown-shows-everyone) - these mislead users or expose data outside intended scope.
2. Appointment cancellation confirmation and the payment screen's missing payment-detail collection - both directly contradict rules you've already written down for this product.
3. Currency/region mismatch (UGX vs. $, Uganda-only emergency content) - needs a product decision on which market this build targets before it's "fixed" rather than just patched.
4. Consolidate on one component library (`app_ui.dart` looks like the intended target per its own docs) and fix `BloomButton`'s 42px height in one place to clear most of the touch-target and visual-consistency findings at once.
